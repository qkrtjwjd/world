## 0-1. 왜 바꿨는가

v7 파서(`process_line`)는 **폴스루 블랙리스트**였다. 마커·대사 패턴을 순서대로 시도하다가
아무것도 안 걸리면 그 줄을 **나레이션으로 그대로 출력**했다. 결과:

- `▶` 마커가 떨어진 연출 지시가 대사로 출력됐다. 플레이어에게 "오프닝 독백에서 이어지며" 같은
  제작 용어가 그대로 보였다 (`Scenario/확인필요.md` 7-3 — 실제로 발생한 버그).
- `※` `【 】` `S#xx` `·` 는 파서가 **아예 인식하지 않아** 전부 나레이션으로 샜다.
- 그래서 사람이 `Scenario/*.txt` 라는 중간 파일을 손으로 만들어야만 했다.

## 0-2. v8의 원칙

**버려지지 않는다.** 조용히 새는 경로가 없는 것이 이 설계의 전부다.

## 0-3. 입력이 .docx 인 이유

화이트리스트의 판정 근거는 **run 단위 볼드·이탤릭**이다. 그 정보는 docx 에만 있고
중간 `.txt` 에는 없다. 따라서 `word/document.xml` 을 직접 읽는다.
외부 라이브러리 없이 표준 `zipfile` + 정규식으로 처리한다.

# **5. 노드 매핑 — `Scenario/node_map.json`**

**파서는 노드명을 추측하지 않는다.** `node_map.json` 이 정한다.

- 정본 1씬이 **여러 노드로 쪼개져 있다** (S#02→3, S#04C→4 등, 총 **21씬 41노드**).
  NightSequenceManager / KitchenTriggerCutscene 이 노드 사이에 클로즈업·무음 연출을
  끼워넣기 때문이다. **임의로 합치지 말 것** (`House_Opening.yarn:12-14`).
- 노드 이름은 **C# 인스펙터 필드에 직렬화**돼 있다. 바꾸면 유니티 재배선이 필요하다.
- 씬의 대사를 노드 순서대로 `count` 만큼 잘라 배분하고, 각 노드의 `anchor`(첫 대사 앞부분)로
  교차 검증한다. **씬 합계가 맞아도 노드 간 배분이 밀리면 앵커가 잡아낸다.**
- 나레이션은 대사와 같은 대화창에 뜨므로 원고 순서대로 섞여 배분된다. 쪽지는 전용 UI 라서 빠진다.
- `by_speaker` · 씬 단위 `anchors` 는 **사람이 대조하기 위한 기록**이다. 파서는 `nodes[].anchor` 만 본다.

정본 15-B 가 반복을 명시하기 때문이다("미루는 같은 말을 반복하며, 같은 행동을 반복한다").
정본 문구로 다시 썼고 `node_map` 에는 넣지 않았다 — 정본 3줄은 이미 `Village_Bakery` 에
배분돼 있고, 루프는 같은 줄의 **재생 방식**이지 별도 대사가 아니다.

**이것이 7-1 절대 규칙의 실제 적용 사례다.** 대응이 없다고 바로 지우지 말고 사람에게 묻는다.
물어본 결과 4개는 폐기, 2개는 정본 근거가 확인돼 존치로 갈렸다.

# **6. 주인공 이름은 "루" 라고 쓰지 않는다 (필수)**

플레이어가 타이틀에서 주인공 이름을 직접 정하므로(`PlayerIdentity`), **표시되는 "루" 는 전부 치환한다.**
파서 마지막 단계에서 `tools/rename_lu_in_yarn.py` 의 `convert_text` 를 재사용한다.

| 자리 | 출력 | 예시 |
|---|---|---|
| 화자 이름 | `{$이름}:` | `{$이름}: 지금 가요.` |
| 받침에 따라 바뀌는 조사 | `{이름조사("가")}` | `{이름조사("가")} 좋아하는 걸 만들어줄게` |
| 받침과 무관한 조사 | `{$이름}` + 조사 그대로 | `{$이름}의`, `{$이름}도`, `{$이름}에게` |

- 조사 함수 인자는 **받침 없는 형태**로 넘긴다: `가` `는` `를` `와` `야` `로` `라` `랑`
- **`<<showSprite "루" ...>>` 의 `"루"` 는 그대로 둔다.** 표시 이름이 아니라 조회 키다.
- `쿠루`·`미루` 는 치환 대상이 아니다 (앞이 한글이면 제외하는 정규식).
  **`미루` 는 v9부터 허용 화자이기도 하다** — 화자명으로 쓰인 `미루` 가 치환되지 않는지 확인할 것.
- 치환은 화자 대사·독백·나레이션·쪽지 **모두**에 적용된다.
  예: 마을 S#15 의 `세라 "…루?"` → `세라: …{$이름}?`

**이 후처리를 빠뜨리면 플레이어 이름 입력 기능이 통째로 무력화된다.**

# **7. 검증 게이트**

`node_map.json` 과 어긋나면 **종료 코드 1**. `gate_report.txt` 에 상세가 남는다.
경고로 넘기지 않는다.

| # | 검사 | 잡는 것 |
|---|---|---|
| 1 | 씬별 합계 == `expected` (21개 항목) | 누락·중복 |
| 2 | **화자별 배분 == `by_speaker`** | 합계는 맞는데 화자가 밀린 경우 |
| 3 | 노드별 대사 수 == `count` | 씬 안에서 노드 간 배분이 밀린 경우 |
| 4 | 노드 **앵커 텍스트** 일치 | 카운트가 전부 맞는데 내용이 어긋난 경우 |

부가: 합계 == `expected_totals` / `node_map` 에 없는 씬에서 통과 항목이 나오면 실패.

## 7-2. 화자별 배분 대조 (게이트 2)

`node_map.json` 의 `by_speaker` 를 **실제로 읽어서** 씬별로 대조한다.
데이터만 있고 파서가 읽지 않는 상태를 두지 않는다 — **`by_speaker` 는 전 씬 필수이며 미등재도 실패다.**

`루독백` 은 **별도 화자로 계상한다.** 화자대사 카운트에 합치지 않는다.

실패 메시지는 씬 합계처럼 뭉뚱그리지 않고 화자별 기대/산출과 **차이의 방향(+/-)** 을 찍는다.
배분 오류는 대개 인접 화자끼리 밀리므로 방향이 원인을 바로 가리킨다.

```
FAIL S#04C  세라: 기대 10 / 산출 11  (+1)
            쿠루: 기대 14 / 산출 13  (-1)
```

`gate_report.txt` 는 씬별 줄에 산출 배분을 함께 찍고, 끝에 화자별 총계를 낸다.

## 7-0. 기대 합계 — **D 실측 기준**

| 구간 | 화자대사 | 루독백 | 쪽지 | 나레이션 | 소계 |
|---|---|---|---|---|---|
| D-1 집 (S#01~S#13) | 59 | 2 | 2 | 1 | **64** |
| D-2 마을 (S#14~S#15) | 19 | 2 | — | — | **21** |
| **데모 총계** | 78 | 4 | 2 | 1 | **85** |

⚠️ **`node_map.json` 의 `expected_totals.dialogue` 값은 `82` 다** (78 + 4).
파서가 루 독백을 `dialogue` 에 합산하기 때문이다 (`KIND_MONOLOGUE` → `SceneBucket.dialogue`).
집의 61은 **화자대사 59 + 루독백 2** 이지 화자대사 61이 아니다.
이 혼동을 막는 것이 게이트 2(화자별 배분)의 존재 이유다.
`gate_report.txt` 는 `대사 82 (화자대사 78 + 루독백 4)` 처럼 쪼개서 찍는다.

`UNCLASSIFIED` 건수는 **실패 조건이 아니다.** 리포트에 적고 사람이 판단한다.
정상이면 **문서 제목·섹션 헤더·에셋 목록만** 남는다.
**거기에 대사가 섞여 있으면 규칙 버그**이므로 매번 눈으로 확인한다.

정본이 개정되면 **`node_map.json` 을 먼저 고친다.** 안 고치면 게이트가 막는다 — 그게 목적이다.

## 7-1. 절대 규칙

- **게이트 기대값을 산출 결과에 맞춰 고치지 않는다.** 숫자가 어긋나면 원인을 찾는 것이 먼저다.
  기대값 변경은 **D 실측을 근거로, 사람의 승인**을 받아서만 한다.
- **승인만 됐고 D 에 아직 없는 사항으로 기대값을 미리 올리지 않는다.** (CLAUDE.md §9-1)
  D 가 정본이므로 D 에 없으면 현재 기준은 "없음" 이다.
  실례: S#07 승격 2줄 — 승인은 났지만 D 에 없어 기대값은 여전히 **0** 이다.
  D 에 들어간 뒤에 S#07 0→2 · 집 64→66 · 총계 85→87 로 올린다.
- **현행 yarn 에만 있고 정본에 없어 차단된 대사는, 삭제하기 전에 사람에게 정본 승격 여부를 묻는다.**
  차단은 규칙이 동작한 것이지 그 줄이 불필요하다는 뜻이 아니다.

# **9. 연출 데이터 (`*_staging.json`)**

`[FILTER] [BGM] [SFX] [UI] [CAM] [TRIGGER]` 블록은 텍스트가 아니라 연출 데이터다.
`.yarn` 에 들어가지 않고 별도 JSON 으로 빠진다.

**이름 지어내기 절대 금지.** 실제 등록된 Yarn 커맨드로 안전하게 매핑되지 않으면
`command: null` + `todo` 로 남기고 사람이 결정한다.
잘못 지어낸 SFX 이름은 런타임에 **조용히 안 울리므로** 가장 위험하다.

정본의 `[TRIGGER]` 는 현재 **전부 미매핑**이다. 이유가 있다:
- `[아이템 획득: 각설탕]` — 아이템 획득 Yarn 커맨드가 프로젝트에 없다
- `인형화 상승` — 수치가 안 적혀 있다. 숫자를 지어낼 수 없다
- `→ S#04G 자동 전환` — 씬 전환이 아니라 노드 전환이고, C# 매니저가 처리한다

## 9-1. 이름의 출처 — 목록을 문서에 복사하지 않는다

**CLAUDE.md §4.** 이름은 코드가 바뀌면 같이 바뀐다. 작업 시점에 코드에서 직접 조회한다.

| 대상 | 출처 |
|---|---|
| Yarn 커맨드 | `[YarnCommand("…")]` 어트리뷰트 + `AddCommandHandler("…")` 등록 (`Assets/Scripts/Dialogue/YarnCommandBridge.cs` 등) |
| 스프라이트 감정 ID | `Assets/Date/Dialogue/CharacterSpriteData.asset` 의 `emotionId` |
| 포트레이트 설정 | `Assets/Resources/PortraitConfigs/*.asset` |
| SFX | AudioManager 등록 목록 |

BGM 경로 형식만 고정이다: `Resources.Load("BGM/파일명")`.

> 목록을 문서에 박아두면 개명 때 반드시 어긋나고, **규약을 따를수록 틀리게 된다.**
> 실제로 이 절에 `open_merchant_ui` 가 남아 있었다 (현재 이름 `open_sol_trade`).
> 상인 → 솔 개명 때 코드만 바뀌고 문서가 따라오지 않은 것이다.
>
> **파서에는 커맨드 목록이 아예 없다.** 이름을 만들어내지 않고, 매핑이 확실하지 않으면
> `staging.json` 에 `command: null` + `todo` 로 남긴다. 그래서 이 목록이 필요 없다.

## 9-2. 포트레이트 좌우 (F-2-2)

`<<showSprite "캐릭터" "감정" [side] [mode]>>`

`PortraitRegistry.GetDefaultSide()` 가 **루=Right / 그 외=Left** 를 강제한다
(`Assets/Scripts/Dialogue/PortraitRegistry.cs:34-40`). side 를 생략해도 이 규칙이 적용된다.
`mode="fixed"` 는 게이지 70+ 시 `_real` 스프라이트 자동 교체를 끄는 스위치다.

## 9-3. 수치 변동 (F-2-1)

`add_corruption` 핸들러는 `YarnCommandBridge.cs:472-475` 에 있다.

**의미가 있는 변동(목격·들림·접촉)은 `applyTrigger` 를 기본으로 쓴다.**
`add_corruption` / `change_gauge` 직접 변동은 트리거로 표현 안 되는 순수 결과값에만 예외적으로 쓴다.
전투 결과처럼 인형화와 게이지가 동시에 움직이면 **둘 다 따로 처리**해야 한다
(트리거 하나로 인형화까지 된다고 착각 금지).

⚠️ `GaugeTriggerRegistry` 의 실제 등록 트리거는 `Assets/Scripts/System/GaugeTriggerRegistry.cs:27-38`
에 있다 (`무서운것_목격` +15, `세라_목소리_들림` -25, `쿠루_직접_대화` +10 등).

# **11. 변환 경계 — 파서가 손대지 않는 것**

- **전투 씬**: 전투(선택지·HP·도주·정화)는 Yarn 대화가 아니라 전투 시스템이다.
  전투 전후 대사만 변환 대상이다.
- **게임플레이 지시**: "플레이어 유도", "이동 튜토리얼 표시" 같은 설계 항목.

  데모는 인형화 0~30 구간만 채우고 31+ 는 빈 칸으로 둔다.
- **파서는 시나리오를 창작·각색하지 않는다.**
